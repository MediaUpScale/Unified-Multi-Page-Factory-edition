### 3.10 DeepInfra `num_inference_steps` — the actual payload, not an assumption

**When:** 2026-08-20 08:49. User required the **exact** request payload vs Together.ai history. Report after Part 1 before Parts 2–3.

#### What was actually sent before the fix

LOFI always *intended* `steps=4` (`LOFI_IMAGE_STEPS = 4` → `TogetherImageGenerator.generate_image(..., steps=4)`). Together.ai used that as a first-class field:

```python
gen_kwargs = {
    "prompt": prompt,
    "model": active_model,
    "width": 768,
    "height": 1344,
    "steps": steps,   # 4
    "n": 1,
    "response_format": "base64",
}
response = self.client.images.generate(**gen_kwargs)
```

After the DeepInfra switch, Schnell went through the OpenAI SDK with `num_inference_steps` only inside `extra_body`. The OpenAI-compat schema (`OpenAIImagesGenerationsIn`) has **no** `num_inference_steps` field. Extra keys can be stripped. DeepInfra’s own playground default if that field is omitted is **`num_inference_steps = 1`** (range 1–50), **not** 4 and **not** 20–30.

So the communication reel was logged as `steps=4` locally, but that was our argument, not proof DeepInfra ran 4 iters. The leading suspect is **1-step Schnell**, which degrades hands/noses the same way the user saw. (User had hypothesized 20–30; the actual mismatch was **1 vs 4**.)

#### Fix (now live)

Native inference POST, steps in the JSON body — not `extra_body`:

```
POST https://api.deepinfra.com/v1/inference/black-forest-labs/FLUX-1-schnell
{
  "prompt": "...",
  "width": 768,
  "height": 1344,
  "num_inference_steps": 4,
  "num_images": 1,
  "guidance_scale": 0.0
}
```

Logged on the 3 probe stills:

`payload={'width': 768, 'height': 1344, 'num_inference_steps': 4, 'num_images': 1, 'guidance_scale': 0.0}`
